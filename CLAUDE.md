# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Context

PROTEA is the target platform for the progressive consolidation of the **PIS** (protein-information-system) and **FANTASIA** codebases. The goal is not a full rewrite but an incremental migration that redesigns the system around a clean separation of concerns: infrastructure, execution flow, and domain logic are deliberately decoupled. Workers in PIS/FANTASIA conflate database sessions, queue management, orchestration, and business logic into single classes: PROTEA is architected to eliminate that coupling.

New capabilities and data model extensions are expected continuously. Architectural decisions must accommodate evolution without regression, and computational efficiency must be preserved or improved at each step.

## Branch and release model

Two branches map to two environments (full runbook: `docs/source/runbooks/release-process.rst`).

- **`develop` = trunk + development environment.** Every change lands here via a PR gated by the test/lint/docs/integration checks. The dev box tracks `develop` HEAD and redeploys from source. A push to `develop` runs the cheap gates only: it never builds a container and never publishes a package.
- **`main` = production line.** A clean sequence of single-commit snapshots of `develop`'s tree, versioned by release-please. Production runs a tagged release, not `main` HEAD.
- **Promote with `scripts/promote.sh [--auto]`.** It snapshots `develop`'s tree onto `main` as one commit (O(1), conflict-free regardless of divergence; never a `git merge`). Merging the promotion PR then lets release-please open the release PR; merging THAT cuts the tag, which is the only event that builds containers and publishes packages (`docker.yml` and the `*-container.yml` workflows are gated to `release: published`).

PRs base `develop`. Never commit to `main` directly; reach it only through `promote.sh`.

## Commands

All commands run from `repositories/PROTEA/`.

```bash
# Install dependencies (including dev group)
poetry install

# Start the full dev stack (API + workers + frontend) in one shot
bash scripts/manage.sh start [N]   # N = number of batch workers per pipeline (default 1)

# Stop everything
bash scripts/manage.sh stop

# Check worker status (PID, RAM, running/dead)
bash scripts/manage.sh status

# Tail logs (interactive picker or direct name fragment)
bash scripts/manage.sh logs [name]

# Add extra workers to a queue without restart
bash scripts/manage.sh scale protea.predictions.batch 2

# Run unit tests
poetry run pytest

# Run a single test
poetry run pytest tests/test_jobs_pg.py::test_name -v

# Expose PROTEA to the internet via Cloudflare Tunnel (no account required)
bash scripts/expose.sh

# Initialize the database schema (first time or after DB reset)
poetry run python scripts/init_db.py

# Dispatch a job (POST /jobs with {operation, payload}) and run a worker to
# consume it from its queue
poetry run python scripts/worker.py --queue protea.jobs

# Apply Alembic migrations
alembic upgrade head
```

Integration tests (requires Docker) use the `--with-postgres` pytest flag: `poetry run pytest --with-postgres`.

Settings load from `protea/config/system.yaml` and are overridden by env vars `PROTEA_DB_URL` and `PROTEA_AMQP_URL`.

## Dev Stack

Prerequisites: Postgres and RabbitMQ must be running before starting the stack.

```
protea/config/system.yaml       ← DB URL and AMQP URL (created manually, not committed)
logs/api.log                    ← FastAPI logs
logs/worker-ping.log            ← Worker for protea.ping queue
logs/worker-jobs.log            ← Worker for protea.jobs queue (insert_proteins, fetch_uniprot_metadata)
logs/frontend.log               ← Next.js dev server
```

**Queue routing** (a summary: each operation's queue is declared by its `OperationSpec` in `protea/core/operation_catalog.py`, and `tests/test_every_operation_declares_its_spec.py` pins all of them):
- `protea.ping` → ping operation (smoke test)
- `protea.jobs` → insert_proteins, extract_goa_universe, resolve_protein_sequences, fetch_uniprot_metadata, load_ontology_snapshot, load_goa_annotations, load_quickgo_annotations, generate_evaluation_set, load_interpro_go_mapping, run_interproscan_batch, predict_go_terms_from_interpro, refresh_goa_release_dates, compute_information_accretion, load_cut_photo, load_homology_table, load_embedding_bank, declare_member_taxa, load_lexicon_bank, load_segment_families
- `protea.embeddings` → compute_embeddings coordinator (serialized: one at a time, retries with 60s delay if GPU busy)
- `protea.embeddings.batch` → compute_embeddings_batch (GPU inference; OperationConsumer, no DB Job row)
- `protea.embeddings.write` → store_embeddings (bulk pgvector insert; OperationConsumer)
- `protea.embeddings.upload` → upload_residue_shard (on the node with the card: puts the residue-code
  shards its batches spooled in `operation.residue_shard_spool_dir` in the artifact store, then hands
  each to `store_residue_codes`; OperationConsumer; ADR-D51)
- `protea.predictions` → predict_go_terms coordinator (partitions queries into batches and dispatches them to `protea.predictions.batch`)
- `protea.predictions.batch` → predict_go_terms_batch (KNN + GO transfer; OperationConsumer, no DB Job row)
- `protea.predictions.write` → store_predictions (bulk GOPrediction insert; OperationConsumer)
- `protea.methods.write` → ingest_method_predictions (a method's own predictions, read from a
  TSV it produced elsewhere, written as a PredictionSet whose score column is `method_score`;
  the write stage stays on the server, like the other `.write` queues)
- `protea.methods` → run_lab_method (a laboratory method's container, run on the node with the card from an
  image pinned by id, on a query FASTA taken from the store by hash; its predictions are enqueued as an
  `ingest_method_predictions` child job on `protea.methods.write`; ADR-D53)
- `protea.evaluations` → run_cafa_evaluation (Fmax / AuPRC / coverage; isolated so long evals don't block the general jobs queue)
- `protea.training` → export_research_dataset (serialized; GPU/RAM-intensive KNN + feature generation + artifact-store upload), export_transitions_dataset (the ADR-D56 transitions tables; see below) and run_count_map (the explainable-units family's count map, ADR-D65). Re-ranker *training* itself no longer runs in PROTEA: see "Re-ranker training decoupling" below.

The frontend (`apps/web/`) is a Next.js 16 app with Tailwind v4. API URL is configured in `apps/web/.env.local` (`NEXT_PUBLIC_API_URL=http://127.0.0.1:8000`).

**Known issue:** Tailwind CSS resolution warnings appear in the Next.js dev server console (`Can't resolve 'tailwindcss'`). These are non-blocking: the app renders correctly. The `npm run build` produces clean output.

## Architecture

### Core Abstractions (`protea/core/`)

**`Operation` protocol** (`contracts/operation.py`): every unit of domain logic implements `name: str` and `execute(session, payload, *, emit) -> OperationResult`. Progress and structured events are reported through the `emit` callback (`EmitFn`), which writes `JobEvent` rows to the DB in real time. Operations are pure domain logic: they receive a session and emit events; they do not manage sessions or queues themselves. Long-running bulk-load operations (`load_goa_annotations`, `load_quickgo_annotations`, `fetch_uniprot_metadata`, `run_cafa_evaluation`) are explicitly allowed to call `session.commit()` per page so that an interrupted job leaves a partial-but-consistent dataset rather than rolling everything back; `BaseWorker` still owns the final transition commit.

**`OperationRegistry`** (`contracts/registry.py`): a dict-backed registry. Operations are registered at startup; `BaseWorker` resolves them by name at dispatch time. Every operation is registered with an **`OperationSpec(domain, kind, queue, purity, resource, family, publishes_to, status)`** (`core/operation_spec.py`, ADR-D60 decision 6), one row per operation in `core/operation_catalog.py`'s `CATALOG`; the registry refuses an operation without one and a queue that would carry both Job ids and operation messages. Queue names in the Python code under `protea/` and `scripts/` live in `core/queues.py`; tests, shell scripts, compose and deploy files, the web app and the docs still spell them.

**`core/utils.py`**: small set of shared utilities (`utcnow()`, `chunks(seq, n)`). The previous `UniProtHttpMixin` is gone. HTTP retry / backoff / Retry-After / cursor handling lives in the `protea-sources` plugins, which every networked operation delegates to; `protea/core/operations/_universe_http.py` was the last in-tree copy and ADR-D49 deleted it. Protein and sequence storage is shared through `core/operations/_protein_store.py` (`store_records`), used by `insert_proteins` and `resolve_protein_sequences`.

**Current operations** (`core/operations/`):
- `insert_proteins`: paginates the UniProt REST API (FASTA format, cursor-based, exponential backoff + jitter), deduplicates sequences by MD5 hash, and upserts `Protein` + `Sequence` rows.
- `fetch_uniprot_metadata`: fetches TSV annotations from UniProt and upserts `ProteinUniProtMetadata` by `canonical_accession`. Fully migrated to PROTEA models: no legacy dependencies.
- `load_ontology_snapshot`: downloads a GO OBO file and populates `OntologySnapshot` + `GOTerm` rows. Versioned by `obo_version` (unique constraint).
- `extract_goa_universe` (`ExtractGoaUniverseOperation`): scans one GOA release and makes every accession it admits exist in `protein` as an **accession-only row** (accession, canonical, isoform split, `first_admitted_release`), so `load_goa_annotations` has nothing left to skip: `protein_go_annotation.protein_accession` is a foreign key and the loader can only drop what is absent. Admission is four tiers declared in the payload (`truth` = the 13 LAFA codes, `curated_inference` = `ISS ISO ISA ISM IGC RCA NAS IKR IRD`, `swissprot_of_release` read from the entry name the GAF itself carries; `IEA`/`IBA`/`IBD`/`ND` excluded), enumerated rather than a complement, so an unknown evidence code is counted and rejected instead of admitted in silence. The evidence predicate reads the RAW GAF columns before a record is built: 0.24% of lines survive it, which is 4.4 minutes a release against 11.5. Opens no connection but the GAF fetch, which makes a release pass a pure function of a cached file and therefore re-runnable. Runs on `protea.jobs`. See ADR-D49.
- `resolve_protein_sequences` (`ResolveProteinSequencesOperation`): fetches sequences, audit dates and merged-accession links from UniProt for every `protein` row that lacks them. Runs ONCE, after the GAF series, because annotations are historical and must be loaded release by release while a sequence is a property of the protein that only today's UniProt has; doing it per release re-asked the same questions and wasted 34% of its requests. Its population is a query (`sequence_id IS NULL`), not a payload field. Three passes with three predicates: sequences, then the merged accessions the batch endpoint does not return (both rows share one `sequence_id`, so a merge costs no extra embedding), then `date_created IS NULL`, which is a much larger population because everything `insert_proteins` loaded has a sequence and no dates. Accessions UniProt no longer serves are written out by name as `sin_resolver.txt`. Transport lives in the protea-sources UniProt plugin; the operation imports no HTTP library. Runs on `protea.jobs`. See ADR-D49.
- `load_goa_annotations`: bulk-loads GO annotations from a GAF file into `AnnotationSet` + `ProteinGOAnnotation` rows, filtered against canonical accessions already in the DB.
- `load_cut_photo` (`LoadCutPhotoOperation`): the server half of ADR-D59. The photo of a cut is built away from the server by `protea.core.cut_photo.build` (a file stage with no database: members, which are the superset, what GOA admits by truth or curated codes and the annotated UniRef50 neighbours of the superset (a cluster co-member with a PAINT or electronic-orthology row), each with its sets and cluster, then every member's rows with their evidence channel, the paired release's Swiss-Prot sequences, the TrEMBL sequences of the members outside Swiss-Prot read out of the release's full knowledgebase archive with its published md5 checked on the stream, and a manifest naming every source and the sha256 of every output); this operation verifies it and writes it. It refuses before writing anything unless the manifest hashes to the sha256 the payload names and is `complete`, every output still hashes to what the manifest recorded, the cut is not after the mark and every source passes `protea.core.source_guards` (GOA published on the cut's date; the paired Swiss-Prot release, the UniRef release of the clusters and the payload's GO snapshot published on or before it; no UniProt or UniRef release at or after the ceiling), the GO snapshot is the one the GAF's header leads to (not newer than the GO release its `!go-version` declares, and no loaded graph between the two, because a cut takes the newest graph not after that release; a GAF 2.1, as GOA wrote up to 2019, declares none and is bound by the cut's date instead), the photo was classified with the channel table this platform declares (rows are stored without their channel, so every reader computes it again) and a table already stored under that digest holds exactly what the code declares, the manifest's Swiss-Prot release is the loaded one (date, entry count and canonical digest), and `sequences.parquet` is that release byte for byte (every md5 recomputed, the accession and md5 table hashed against the release's digest); a manifest that lacks an output this builder writes is refused, and every TrEMBL sequence must hash to its md5. Then, in the job's transaction: the channel table when it is not stored yet (`evidence_channel_table` and its rows, written once), the annotation set of GOA t (created, or the existing one when it is on the same snapshot), accession-only `protein` rows with `first_admitted_release` written as a minimum, the superset's and the TrEMBL sequences in `sequence` by md5 (`protein.sequence_id` keeps today's sequence; the paired one is read through `swissprot_membership`, and for every member through `cut_photo_member.sequence_md5`), every member row whose GO term the snapshot knows (the others are counted and named in an event), and the `cut_photo` row with its kind (`full`, or `truth_only` for a cut that only ends a window: no neighbours, no TrEMBL, no UniRef release; 205 in this campaign), its ADR-D58 descriptors (`photo-<cut>`) and its manifest stored in the artifact store by URI and sha256, then one `cut_photo_member` row per member. A cut has one photo: the same manifest again is a no-op and another one is refused. Runs on `protea.jobs`.
- The homology table of a cut (ADR-D61) is built away from the server too, by `protea.core.homology.build` (a file stage with no database, shipped in `builder_files.txt` and run by `deploy/cluster/homology_build.sh`): `prepare` reads a complete full photo already on the cluster (each input checked against `photo.json`) and writes the superset's unique sequences as queries and every member's as the bank, keyed by md5; `search` runs a pinned MMseqs2 (`18-8cc5c`, binary sha256 checked) with its defaults and writes `hits.parquet` (`query_md5`, `target_md5`, `fident`, `alnlen`, `qcov`, `tcov`, `evalue`, `bits`; self hits dropped and counted, no threshold of ours); `manifest` writes `homology.json` (`complete`, `measurement` for a sampled run, or `refused`). The exclusion groups are the photo's UniRef50 clusters (`cut_photo_member.cluster`).
- `load_homology_table` (`LoadHomologyTableOperation`): the server half of ADR-D61. It refuses before writing anything unless `homology.json` hashes to the payload's sha256 and is `complete` (a sampled `measurement` never loads), `hits.parquet` still hashes to what it recorded and holds the hits it counted, the photo it names is the loaded full photo of that cut (found by the photo manifest's sha256), and every query is the sequence of a superset member and every target the sequence of a member of that photo. Then it puts the hits and the manifest in the artifact store (`homology/<cut>/<sha>/`) and writes one `homology_table` row with its ADR-D58 descriptors (`homology-<cut>`). A cut has one table: the same manifest again is a no-op and another one is refused. Runs on `protea.jobs`.
- The embedding bank of the photos (ADR-D62) is computed away from the server too, by `protea.core.embedding_bank.build` (a file stage with no database, shipped in `builder_files.txt` and run by `deploy/cluster/embedding_bank_prepare.sh` and `embedding_bank.sh` in the cluster's own environment, with the protea-backends plugins): `prepare` writes every member sequence of the photos named once, by md5, length-sorted and cut into shards of about eight million tokens; `embed` runs one configuration on one card through the plugin's padded pass (`embed_chunks_padded`, batches under a token budget), shard by shard, resumable, stopping before the job's limit; `compare` embeds a sample one sequence per pass and padded and records the gap and both speeds; `manifest` writes `bank-<config>.json` (`complete`, or `refused` when a shard is missing or changed, a vector is not finite, or the shards mix weights revisions, software or cards). Vectors are half precision, cast with the store path's rule.
- The lexicon bank of the photos (ADR-D63) is decoded away from the server by `protea.core.lexicon_bank.build` (shipped in `builder_files.txt`, run by `deploy/cluster/lexicon_bank.sh` on one card): over the population an embedding bank prepared, `cut` writes per sequence its best path's segments (start, end, theme) and every residue's column, `mass` its theme mass (sparse), and `manifest` writes `lexicon/<name>/lexicon-bank.json` with the lexicon's sha256, the parity record against the laboratory's code and every shard's sha256. The decoder is `protea.core.lexicon` (inference only: the checkpoint's tables, the candidates, the exact Triton passes and the traceback), ported from the laboratory with its cut identical and its theme mass within two half-precision steps; Triton kernels are exempt from the smell budget's parameter limit only.
- The segment families of a cut (ADR-D65, decision 2) are built away from the server by `protea.core.segment_families.build` (shipped in `builder_files.txt`, run by `deploy/cluster/segment_families.sh` on CPU): `prepare` checks the photo and a complete lexicon bank and writes the cores of the segments of the donors (the photo's truth members) and of the targets (its other superset members), by sequence md5 and with no label read; `search` runs the laboratory's three MMseqs2 searches with the pinned binary (donor cores against themselves, their reverses as decoys, target cores against them); `families --scope strict|permissive` masks the decoy components, links, groups by set cover, joins groups by profiles calibrated on reversed representatives, joins families into clans by partial links and gives each target segment its best link's family (`families-<scope>.parquet`); `manifest` writes `segment-families.json`. The steps are `protea.core.segment_families.algorithms`, a port of the laboratory's `familias_tramos.py` (set cover, components and cores identical to its functions).
- `load_segment_families` (`LoadSegmentFamiliesOperation`): the server half of the segment families. It refuses before writing anything unless `segment-families.json` hashes to the payload's sha256, is `complete` and declares the `segment_families` table, the photo it names is the loaded full photo of its cut (by manifest sha256), the lexicon bank it names is loaded (by manifest sha256 and name), was decoded with the lexicon it names and covers that photo, every output this builder writes (`segments.parquet` and `families-<scope>.parquet` for both scopes) is present, hashes as recorded and holds one row per segment, and every donor md5 is the sequence of a truth member of the photo and every target md5 that of another superset member. Then it puts the outputs and the manifest in the artifact store (`segment-families/<lexicon>/<cut>/<sha>/`) and writes one `segment_families` row (descriptors `families-<lexicon>-<cut>`). A photo and a lexicon bank have one: the same manifest again is a no-op and another one is refused. Runs on `protea.jobs`.
- `load_lexicon_bank` (`LoadLexiconBankOperation`): the server half of ADR-D63. It refuses before writing anything unless the manifest hashes to the payload's sha256, is `complete` and is that lexicon's, the payload's weights are a registered `lexicon` (`model_weights`) with the sha256 the bank and its parity record name, every photo it names is loaded, every shard of both passes hashes as recorded and holds its rows, and the cut's md5s are exactly the photos' member md5s (`_bank_population`, shared with `load_embedding_bank`). Then it puts every shard and the manifest in the artifact store (`lexicon-banks/<name>/<sha>/`) and writes one `lexicon_bank` row (descriptors `lexicon-<name>-cuts-<cuts>`). Runs on `protea.jobs`.
- `run_count_map` (`RunCountMapOperation`): the explainable-units family's first source fitted and read inside the platform (ADR-D64, ADR-D65). For a window t0 -> t1 it reads every protein's state at t0 (`protea.core._cut_state`: the evaluator's own t0 side with t0's NOT terms only, measured on 211 -> 227 to equal the stored `known` except the 47 proteins a NOT of 227 touches), the donors (the photo's truth members) and the targets (the proteins the window's truth scores) by their sequence md5, and their units: the lexicon's themes from a loaded lexicon bank (`units` `themes`, the default), or the families of one scope of loaded segment families of that photo under that bank (`units` `families` with `segment_families_id` and `scope`; a core no family took or a masked one gives no unit); per aspect it fits m on the donors alone and reads the targets (`protea.core.count_map`: a port of the laboratory's `mapa_cuentas.py`, bit-identical to its `Fit`). It registers the map as `count_map` weights fitted on t0's annotation set, derives the `method` row from its spec (instance at t0; pins: lexicon, bank manifest, the families' manifest when they give the units, map; a themes run's spec is the one it was before families existed, so its method keeps its id) and writes one prediction set with `method_score` rows and one `prediction_explanation` per row (`protea.core.method_write`, the way any native method writes). The same method over the same window again is a no-op. Runs on `protea.training`; every run needs the author's word (ADR-D64, decision 6).
- `declare_member_taxa` (`DeclareMemberTaxaOperation`): gives the members of a photo loaded before `cut_photo_member.taxon_id` existed their own NCBI taxon, read from the photo's own `rows.parquet` (checked against the photo's manifest) by the rule `load_cut_photo` now applies to every new photo (`protea.core.cut_photo.taxa.member_taxa`: the first taxon of the GOA taxon field; a member whose rows name two own taxa, or that has no rows at the cut, stays NULL and is counted). Runs on `protea.jobs`.
- `load_embedding_bank` (`LoadEmbeddingBankOperation`): the server half of ADR-D62. It refuses before writing anything unless the manifest hashes to the payload's sha256, is `complete` and is the payload's configuration, the stored configuration is the manifest's recipe field for field, every photo it names is loaded (by manifest sha256, cut and kind), every shard hashes as recorded and holds its rows, and the bank's md5s are unique, each a `sequence` row, and exactly the photos' member md5s. Then it puts the manifest in the artifact store (`embedding-banks/<config>/<sha>/bank.json`), writes the `embedding_bank` row (descriptors `bank-<model>-cuts-<cuts>`) and loads the shards one transaction each (binary COPY into a temporary table, then an INSERT into `sequence_embedding` naming the bank, keeping and counting a row already there). A rerun resumes at the first shard not loaded; a loaded bank is a no-op. Runs on `protea.jobs`.
- `load_quickgo_annotations`: streams GO annotations from the QuickGO bulk download API (TSV), with optional ECO→evidence code mapping, pagination, and per-page commits.
- `generate_evaluation_set`: materializes a `EvaluationSet` by snapshotting the ground-truth annotations for a target ontology snapshot / accession set, used downstream by `run_cafa_evaluation`. Its `target_population` says which proteins the window may score: `every_protein` (the default, what every earlier window did) or `superset_at_t0`, the superset of the photo whose annotation set is the window's start (`protea/core/_window_population.py`; the author's rule for the four windows of the frame, ADR-D60), which keeps that population in every bucket of the ground truth and counts by bucket the proteins it left out. It is part of the window's identity, beside the three truth rules.
- `run_cafa_evaluation`: runs the standalone `cafaeval` fork against a `PredictionSet` and persists `EvaluationResult` rows (Fmax, AuPRC, coverage, per-aspect breakdowns).
- `export_research_dataset`: runs KNN + feature generation over temporal snapshot pairs and publishes `train.parquet` + `eval.parquet` + `manifest.json` to the configured artifact store (local FS or MinIO). Inserts a `Dataset` row once upload completes. Consumed by `protea-reranker-lab` for offline LightGBM training.
- `ping`: smoke-test operation.
- `load_interpro_go_mapping` (`LoadInterProGoMappingOperation`): downloads the EBI InterPro2GO flat file and upserts `(ipr_accession, go_id)` mappings; idempotent per release version. Runs on `protea.jobs`.
- `run_interproscan_batch` (`RunInterProScanBatchOperation`): annotates proteins in fixed-size chunks via InterProScan, resumable through release-floor filtering. Runs on `protea.jobs`.
- `predict_go_terms_from_interpro` (`PredictGOTermsFromInterProOperation`): predicts GO terms by joining InterPro hits against the InterPro2GO mapping, aggregates per-protein votes, and emits a tagged `PredictionSet`. Runs on `protea.jobs`.
- `archive_ontology_snapshot` (`ArchiveOntologySnapshotOperation`): fetches the raw OBO for an `OntologySnapshot` and archives it gzipped in the `ArtifactStore`, recording `obo_uri` and the sha256 of the uncompressed bytes. Before storing, it gates the fetched file against the database: the `data-version` header must match `obo_version`, and every non-obsolete `go_id` already loaded must still be present (`max_term_drift_pct`, default 0.0). Terms added upstream are tolerated and counted; missing terms raise `OntologyDriftError` rather than recording a newer ontology under an existing snapshot's identity. The congruence parser is intentionally separate from `LoadOntologySnapshotOperation._parse_terms`, since a check that reuses the parser it checks cannot see a parser-level disagreement. `run_cafa_evaluation._resolve_obo` prefers the archive and verifies the hash, falling back to `obo_url` with a warning. Runs on `protea.jobs`.
- `compute_information_accretion` (`ComputeInformationAccretionOperation`): computes the Information Accretion table cafaeval weights `f_micro_w` by, over an `OntologySnapshot` DAG and an `AnnotationSet` corpus restricted to an evidence regime, and publishes the TSV through the `ArtifactStore`. IA is estimated from term frequencies, so it is identified by three axes (snapshot, corpus, evidence regime), all three pinned on the `InformationAccretionSet` row (the two FKs plus a closed-vocabulary column) together with the resolved code list, a content sha256 and the shape counters. Structural invariants (acyclic DAG, roots at exactly 0, no negative IA, no child holding more proteins than its parents' intersection, drop rate under a threshold, not an all-zero table) are gates that raise, because `protea.core.ia.term_ia` clamps a broken propagation to 0.0 rather than failing. Consumed by `run_cafa_evaluation` via `information_accretion_set_id`, which verifies the hash after fetching. Supersedes `scripts/compute_ia_for_snapshot.py`, which pinned only the snapshot, offered no evidence predicate, and wrote a machine-local `file://` URL. Runs on `protea.jobs`.
- `refresh_goa_release_dates` (`RefreshGoaReleaseDatesOperation`): scrapes the EBI FTP index (`ftp.ebi.ac.uk/pub/databases/GO/goa/old/UNIPROT/`), extracts the official publication date for each `goa_uniprot_all.gaf.<N>.gz` release, and upserts `source_published_at` onto matching `goa` AnnotationSet rows. Backs the temporal release-timeline component on `/evaluation`. Runs on `protea.jobs`.

- `count_backend_parameters` (`CountBackendParametersOperation`): loads each distinct embedding checkpoint through its own backend plugin and writes the parameters that backend's forward path actually executes onto the matching `EmbeddingConfig.param_count` rows. Counts the executed module rather than the published total, because two deployed checkpoints run something smaller than the model they are named after: the deployed ProtT5 is encoder-only (1.208B against a published figure near 3B) and ProtST loads a protein tower and a text tower but calls `model.protein_model` alone (655.3M executed against 766.2M loaded). Grouped by `(model_backend, model_name)`, so configurations differing only in layer selection or pooling share one load. The `EXECUTED_SUBMODULE` map duplicates knowledge that lives in the backend, so `tests/test_count_backend_parameters.py` reads each backend's source and fails when the named attribute stops appearing in its forward path; a missing attribute raises rather than falling back to the loaded total. Defaults to CPU, since `numel` is device-independent. Runs on `protea.jobs`. Exists because the column was NULL for the entire T5 family, which made every size-sorted analysis select its sample on a variable correlated with the outcome.

- `export_evaluation_targets` (`ExportEvaluationTargetsOperation`): writes an `EvaluationSet`'s delta proteins as a FASTA and publishes it to the artifact store, so the same bytes are both the LAFA `--query_file` and the `QuerySet` the internal grid dispatches against. Exists to close an asymmetry: `apps/method_runtime/protea_predict.py` REQUIRES `--query_file`, while `PredictGOTermsPayload` leaves `query_set_id` and `query_accessions` optional and silently selects every protein with an embedding when neither is given. That is a comparability defect before it is a cost one, since a grid scoring one population and a submission scoring another produce numbers that are not about the same thing. Targets are the union of the `nk` / `lk` / `pk` maps, the proteins that GAINED annotation; `removed` holds proteins that only lost annotation, which the evaluation reports and never scores, and requesting it as a category raises. Accessions are sorted and sequences wrapped at a fixed width so the same evaluation set always produces the same bytes, and the returned sha256 is what lets both consumers prove they scored one population rather than assert it. Headers are bare accessions, which round-trip through LAFA's parser unchanged. Delta proteins with no stored sequence are emitted as a warning rather than dropped silently. Runs on `protea.jobs`.

- `declare_query_set_provenance` (`DeclareQuerySetProvenanceOperation`): recovers a hand-registered `QuerySet`'s derivation by **verifying** it rather than reading it out of the description. Four sets were registered through the FASTA upload endpoint by a person, with the window as an id prefix, the job as a word and the sha as a string nothing compared against; migration `c5e8d1a30b72` gave the table the columns and deliberately declared nothing, because recovering a derivation is a judgement that belongs in a job with its events. For each named set it finds every SUCCEEDED `export_evaluation_targets` whose published target count equals the entry count, fetches each one's FASTA through `fetch_and_verify` with the key **derived** from what the job declared (`targets_key_for`, the one spelling, so no later reader has to split a stored uri the way the ground truth's second door did), and writes the window, sha256, job and revision only when the accession set in those bytes equals the set's entries exactly. The uri it stores is the one that export's own `put` returned, taken from the event and checked to END in the derived key: neither is parsed, and building one here would mean guessing the bucket. The revision is not picked either, since a requeued job has more than one start: it counts the DISTINCT values and leaves NULL unless there is exactly one, because for a provenance field "cannot say" beats "the earlier one". Measured 2026-11-08: no export job records that field in any event, so all four recoveries get NULL and the operation reports it rather than writing a quiet one. Verification happens BEFORE the collapse, which the data forces: two jobs published the same digest for the same window under different `output_name` values, so the same bytes live under two keys, and collapsing first could keep the one whose object is gone. A count that matches is a coincidence waiting to happen; a set that matches is the population. Jobs publishing the same `(window, digest)` are one export run twice and collapse to the earliest; two publishing different ones are an ambiguity it refuses rather than resolves. A set with no candidate stays `legacy_undeclared` and is reported, which is the honest outcome for the one from the quick-annotation flow. A description somebody wrote is kept. `dry_run` writes nothing. Runs on `protea.jobs`.
- `export_transitions_dataset` (`ExportTransitionsDatasetOperation`): writes the ADR-D56 transitions dataset's declared tables for named windows on a declared term axis. Separate from `export_research_dataset`, which keeps writing the D45 pair table: two datasets, and mixing them would make one `dataset` row unable to say which it is, so the names here carry a `transitions-` prefix. **Windows are named by id, never by a version pair**, because the pair stopped identifying a window (62 of 69 pairs carry more than one), and each is refused if it pivots on another axis than the one declared or was built by a revision other than the running one unless the payload names that revision; admitting them in bulk with a boolean would be the same as not checking. `cut` (the `ontology_snapshot_id` indexing `terms` and `term_ancestors`) and `cut_version` (the GOA release the laboratory's leakage rule compares against) are two fields and neither is derived from the other. It refuses a window whose `version_t_prime` is after `cut_version`, because its gain is in the model's future: the first run declared `cut_version` 211 over 64 windows and **15 of them ended after 211**, all inside the span the long validation window scores. Each window's truth, releases and horizon are read ONCE into a `WindowFacts`, since two loads are two chances for one bundle's tables to be about different reads, and a window missing a `source_version` or a publication date is refused rather than written as NULL (a NULL version does not fail the leakage rule, it skips it). Today it writes six of the ten, including `gains` (the truth itself: which terms each query gained, with its stratum and the closure the gain is expressed in, 9.6M rows over the 65 admissible windows, sharing the query population as a guard rather than a filter so a gain for a protein `queries` excludes is refused rather than dropped); `window_terms_out`, the axis terms a window's rule leaves out; `residue_refs`, which names where each sequence's per-residue codes live (683,887 references over 5,344 shards, not one byte of code copied) and covers the WHOLE bank, a superset of any window selection, refusing a config with no rows because the rows are keyed by the VOCABULARY config and not by the model config it was derived from, which has zero; `terms` and `term_ancestors`, which are keyed by `cut` ALONE and so need no window list at all (43,558 live terms with their aspect and 595,072 closure pairs on the campaign axis, measured, against the 783,477 `Dag.closure`'s docstring quotes for a different release); and `queries`, whose population is `delta_accessions` imported from the target export rather than restated; both carry the full `evaluation_set_id` as the join key and the writer asserts the two tables agree about their window set before publishing either, because the loader joins them as text and a mismatch silently stops restricting the negatives. It **verifies the vectors before writing them: `terms` carries `vector_uri` and `vector_sha256` for the axis's text-embedding artefact, and the operation FETCHES those bytes and checks the digest before publishing either column, refusing when the artefact is absent, because a sha copied from a message is a locator for bytes nobody checked. It writes no `Dataset` row** while any of the ten tables is unwritten, since a half bundle with a sha is a bundle that lies. Asking for a table ADR-D56 declares but this revision does not write yet is refused rather than skipped. Runs on `protea.training`.

These three operations form the **post-reranker functional-enrichment stage, the last component to be developed before uploading results to LAFA**. All three are fully wired and registered in the `OperationRegistry`; the remaining prerequisite is an InterProScan binary install on the host.

**Internal helpers** (not registered as standalone operations):
- `TrainRerankerAutoOperation` (in `protea/core/training_dump/_runner.py`, with loaders in `protea/core/_training_dump_loaders.py` and reusable helpers in `protea/core/training_dump_helpers.py`) is importable but **not** wired into the `OperationRegistry`. LightGBM training has been moved to [`protea-reranker-lab`](https://github.com/frapercan/protea-reranker-lab); this class survives only as the in-process KNN + feature-generation runner that `ExportResearchDatasetOperation` reuses in `dump_only` mode to produce frozen parquet shards. The old `TrainRerankerOperation` and the standalone `protea/core/operations/train_reranker.py` module were deleted in F0 (T0.6); any external doc or commit still referencing that path is stale.

### Job Lifecycle (`protea/workers/base_worker.py`)

`BaseWorker.handle_job(job_id)` uses **two separate sessions** by design:
1. **Claim session**: transitions `QUEUED → RUNNING`, flushes `job.started`.
2. **Execute session**: resolves the operation, runs it, transitions to `SUCCEEDED` or `FAILED` (storing `error_code` / `error_message`).

Every state transition is recorded as a `JobEvent` row for a full audit trail. Message stages run under `OperationConsumer` (`protea/infrastructure/queue/consumer.py`), whose transient failures are bounded (ADR-D60, phase 3, `queue/_retry.py`): `RetryLaterError` and a lost connection to the database, the broker or the object store (`is_connection_error`, which also looks through wrapped causes) are republished after a wait (the error's own `delay_seconds`, or an exponential backoff) with the `x-protea-retry` header raised, and dead-lettered with a `child.retry_exhausted` event once it reaches `queue.transient_max_retries`; CUDA out-of-memory keeps its own `x-oom-retry` count and cap. This is the primary extension point: new worker implementations (e.g. queue-driven) must preserve this two-session pattern and the `emit` contract.

### HTTP API (`protea/api/routers/jobs.py`)

FastAPI router at `/jobs`. The `session_factory` is injected via `app.state.session_factory` (set at app startup: not hardcoded in the router). Endpoints: `POST /jobs`, `GET /jobs` (filterable by `status`/`operation`), `GET /jobs/{id}`, `GET /jobs/{id}/events`, `POST /jobs/{id}/cancel`. `POST /jobs` answers 422 before writing anything for an unregistered operation, an operation whose kind never gets a Job row (a message stage or a write), and a `queue_name` other than the one its `OperationSpec` names; only the `ping` probe may go to any job queue.

### Data Model (`protea/infrastructure/orm/models/`)

- **`Sequence`**: deduplicated by MD5 hash. Multiple `Protein` rows can reference the same `Sequence`: `sequence_id` is explicitly non-unique.
- **`Protein`**: one row per UniProt accession (including isoforms `<canonical>-<n>`). Isoform parsing via `Protein.parse_isoform()`. Grouped by `canonical_accession`. Has a viewonly relationship to `ProteinUniProtMetadata`.
- **`ProteinUniProtMetadata`**: raw UniProt functional annotations keyed by `canonical_accession`.
- **`OntologySnapshot`**: one row per loaded OBO file release. Versioned by `obo_version` (unique).
- **`GOTerm`**: one row per GO term per snapshot. `(go_id, ontology_snapshot_id)` is unique.
- **`AnnotationSet`**: groups a batch of annotations by source (`quickgo`, `goa`) and ontology snapshot.
- **`ProteinGOAnnotation`**: association between a protein accession and a GO term within an annotation set. Stores qualifier, evidence code, assigned_by, db_reference, with_from, annotation_date.
- **`CutPhoto`** / **`CutPhotoMember`** (ADR-D59, decision 3): the photo of a cut, one row per cut naming its GOA annotation set, ontology snapshot, paired `SwissProtRelease`, UniRef release and cluster table digest, GO_REF list and channel table digest, manifest (JSONB, URI and sha256), job, loader revision and builder revision, with ADR-D58 descriptors; and one row per member with the sets it entered by (`superset`, `truth`, `curated`, `neighbour`; a neighbour by that set alone, never an evaluation target), its UniRef50 cluster, the md5 of its sequence in the paired release (Swiss-Prot or TrEMBL) and its own NCBI taxon as the cut's GOA rows name it (`taxon_id`, migration `c3a9e7d1f5b2`; NULL without rows or with two own taxa). Neighbours enter by UniRef, which no annotation records, so membership is stored, not derived. The per-cluster profiles and the separate cluster table of the first draft were retired by migration `384568a09847`. Written only by `load_cut_photo`.
- **`HomologyTable`** (ADR-D61): one row per cut photo declaring its homology table: the hits parquet in the artifact store by URI and sha256 (the photo's superset searched against all its members by sequence md5 with a pinned MMseqs2), the MMseqs2 version and binary sha256, the command line, the counts, the manifest by URI and sha256, the job and both revisions, with ADR-D58 descriptors. The hits are not database rows. Written only by `load_homology_table` (migration `c7d2e4f9a1b3`).
- **`EvidenceChannelTable`** / **`EvidenceChannel`** / **`EvidenceChannelEmptyGoRef`** (ADR-D59, decision 2): the evidence channel of a GOA row as a declared table, keyed by what it depends on. One row per version, named by the digest every photo records (`cut_photo.channel_table_sha256` is a foreign key to it) and dated by the day GO's GO_REF list was read; its 92 keys (evidence code, reference class, reviewed) with their channel, `*` standing for any reference of a code that decides its channel alone; and how it reads a `GO_REF` with no number through its with/from. The SQL functions `evidence_reference_class(table, db_reference, with_from)` and `evidence_channel_of(table, code, db_reference, with_from, reviewed)` classify a stored row without Python (NULL for a key the table does not list); the postgres tests pin both to `protea.core.cut_photo`. Seeded by migration `f0e6749f94cb` with the first table of 2026-11-16 (86 keys, `781a0ac1`); the current one (`ce0089ab`, with the three obsolete references GOA 160 to 194 carry) and any later one is written by the first `load_cut_photo` that classifies with a new one; never changed.
- **`EmbeddingConfig`** / **`SequenceEmbedding`** / **`PredictionSet`** / **`GOPrediction`**: embedding provenance, per-sequence halfvec embeddings (migrated 2026-04-11), one row per KNN prediction run, and its per-candidate GO term rows (with re-ranker feature columns).
- **`EmbeddingBank`** (ADR-D62): one row per configuration's bank over a set of photos, as its verified manifest declared it: the photos by manifest sha256, the counts, the weights' commit, the software, the card, the token budgets of the padded pass, the manifest by URI and sha256, the loading status (`loading` with `shards_loaded` as the resume point, then `loaded`), the job, both revisions and ADR-D58 descriptors. `sequence_embedding.embedding_bank_id` (nullable, not indexed) names the bank that wrote a row; NULL is a row the queue computed. Written only by `load_embedding_bank` (migration `b8e3f1c6d2a4`).
- **`LexiconBank`** (ADR-D63): one row per lexicon's bank over a set of photos: the lexicon's registered weights, the photos, the counts, every shard of the cut and the theme mass by URI and sha256 (files in the store, not rows), each pass's runs, card and software, the parity record, the manifest by URI and sha256, the job, both revisions and descriptors. Written only by `load_lexicon_bank` (migration `e7c4a9b2d5f1`).
- **`SegmentFamilies`** (ADR-D65, decision 2): one row per cut photo and lexicon bank declaring their segment families: the photo and the bank (foreign keys), the scopes, the segment count, every output (`segments.parquet`, `families-<scope>.parquet`) by URI and sha256 with its rows, the counts of every pass, the MMseqs2 binary and commands, the manifest by URI and sha256, the job, both revisions and ADR-D58 descriptors. The families are files, not rows. Written only by `load_segment_families` (migration `d1f5a8c3e7b2`).
- **`Method`** / **`MethodTrainingWindow`** / **`MethodPin`** / **`PredictionExplanation`** (ADR-D60, decision 3): a method's own identity. `method.id` is uuid5 over the canonical JSON of its `MethodSpec` (`protea/core/contracts/method.py`, namespace pinned there) and a `before_insert` listener refuses an id the spec does not derive; pins are held by role and sha256, training windows by evaluation set id with the role `fit` or `holdout`, explanations per (prediction set, accession, GO term). `prediction_set.method_id` names the method, `embedding_config_id` is nullable, and `ck_prediction_set_has_a_producer` requires one of the two; readers join both OUTER. The leakage guard (`protea/core/_evaluation_leakage.py`) refuses a method whose instance cut, training windows or dated pin references end after the frame starts. The three families (`embedding-reranker`, `world-model`, `explainable-units`) and their descriptors live in `protea/core/families.py`; their introductions are the author's text and stay empty until he writes them.
- **`Dataset`**: frozen re-ranker dataset published by `export_research_dataset` (or the legacy `scripts/dump_reranker_dataset.py`). Unique by `name`. Stores `storage_backend` + `key_prefix` + `train_uri` / `eval_uri` / `manifest_uri` (opaque URIs resolved by `ArtifactStore`), content fingerprints (`schema_sha`, `manifest_sha`), row counts, dump parameters (`k`, `annotation_source`, `embedding_config_id`, `ontology_snapshot_id`, `train_snapshot_pairs`, `eval_snapshot_pair`), and producer provenance (`producer_version`, `producer_git_sha`). The lab's `pull_dataset.py` resolves by id or name.
- **`RerankerModel`**: a trained LightGBM booster registered for inference. Booster bytes live either inline (`model_data`, legacy) or by reference (`artifact_uri`, preferred). Provenance: `feature_schema_sha` (load-bearing at inference: predict refuses to use a booster whose schema drifts from the live pipeline), `dataset_id` (FK → `Dataset` the lab consumed), `external_source` (e.g. `"protea-reranker-lab@<sha>"`), `spec_yaml`, `metrics`, `feature_importance`.
- **`EvaluationSet`** / **`EvaluationResult`**: frozen ground-truth snapshot for a CAFA-style evaluation and the Fmax / AuPRC / coverage metrics persisted by `run_cafa_evaluation`. A window's identity (`uq_evaluation_set_identity`) is nine columns: the two annotation sets, the pivot and the two native graphs, the three truth rules (`truth_profile`, `toi_rule`, `not_codes`) and `target_population` (migration `e5b1c9d3a7f2`).
- **`InformationAccretionSet`**: one computed IA table, unique by `(ontology_snapshot_id, annotation_set_id, evidence_regime)`. Holds the resolved `evidence_codes`, the `artifact_uri` in the object store, a `content_sha256`, and the shape counters (`term_count`, `nonzero_count`, `annotation_count`, `protein_count`, `propagated_pairs`, `ia_max`, `ia_mean`). The counters make a wrong-provenance table visible from its own row: on the v226 pivot the same snapshot and corpus give `ia_max` 18.956 / `ia_mean` 3.261 over all evidence versus 15.943 / 2.681 over the LAFA regime. The legacy `ontology_snapshot.ia_url` column survives as a resolution fallback and is not dropped.
- **Every set says what it is and who made it** (the sets gate, `scripts/check_sets.py --strict`, run strict in CI since phase 2): each table in its `EXPECTED` list declares what it derives from (foreign keys), a `description` its writer derives (ADR-D58's long descriptor), a sha256 for every URI and the job and code revision that made it. Migration `d2f6a8c4e0b7` gave `annotation_set`, `evaluation_set`, `information_accretion_set`, `prediction_set` and `dataset` the columns they lacked (nullable: NULL on an older row reads as "nothing says"), and every writer fills them; `prediction_set`'s code column is `producer_git_sha`, because `meta["code_revision"]` is the revision that identifies the method in `protea/core/method_seal.py`.
- **`Job` / `JobEvent`**: job queue state machine and structured event log. `payload`, `meta`, and `fields` are PostgreSQL `JSONB`.

### Re-ranker training decoupling

LightGBM training has been moved out of PROTEA into the standalone [`protea-reranker-lab`](https://github.com/frapercan/protea-reranker-lab) repo. PROTEA owns the KNN + feature pipeline, dataset publishing, and inference; the lab owns training, evaluation, and booster production. The two repos talk via the artifact store (MinIO in prod, local FS in dev) and a thin HTTP surface on PROTEA.

**Flow:**
1. `POST /datasets` → enqueues an `export_research_dataset` job on `protea.training`. The worker runs KNN + feature generation, uploads `train.parquet` / `eval.parquet` / `manifest.json` via `ArtifactStore`, and inserts a `Dataset` row.
2. The lab's `pull_dataset.py` hits `GET /datasets/{id_or_name}`, resolves the URIs, downloads the dump, trains a LightGBM booster, and writes `runs/<run_id>/{model.txt, spec.yaml, run.json}`.
3. `POST /reranker-models/import` (multipart) or `POST /reranker-models/import-by-reference` (JSON, booster already in MinIO) → uploads the booster if needed, validates `feature_schema_sha`, and inserts a `RerankerModel` row linked back to the `Dataset` via `dataset_id`.
4. Inference consumes registered `RerankerModel` rows via the scoring router (`GET /scoring/prediction-sets/{id}/score.tsv`, `…/metrics`, `…/reranker-metrics`). Boosters are loaded from `artifact_uri` (or inline `model_data` on legacy rows) and scored with `protea.core.reranker.predict`. There is no in-PROTEA training endpoint: `TrainRerankerAutoOperation` survives only as an internal helper used by `export_research_dataset` in `dump_only` mode and should not be exposed by new code.

Related HTTP routers: `protea/api/routers/datasets.py` (dataset registry), `protea/api/routers/reranker_models.py` (model registry + import).

### Testing

Integration tests require `--with-postgres`. The `conftest.py` `postgres_url` session-scoped fixture pulls the Postgres image `docker-compose.yml` pins (`pgvector/pgvector:pg18` by digest, `_DEFAULT_PG_IMAGE`) via Docker, waits for readiness, enables the `vector` extension, yields the connection URL, then tears down the container. Configurable via: `PROTEA_PG_IMAGE`, `PROTEA_PG_USER`, `PROTEA_PG_PASSWORD`, `PROTEA_PG_DB`, `PROTEA_PG_PORT`, `PROTEA_PG_TIMEOUT`. The integration workflow runs the same reference as its service container, and `tests/test_ci_services_match_the_stack.py` fails when the compose file, the workflow and the fixture disagree. The workflow also starts the stack's RabbitMQ, pinned the same way, and exposes it as `PROTEA_TEST_AMQP_URL`; a test that must reach a real broker is marked `broker` and skips where none is offered (the first is `tests/test_the_broker_confirms_before_the_ack.py`), because the autouse `_no_live_broker` fixture refuses every other pika connection. The publisher (`queue/publisher.py`) runs each attempt in confirm mode with `mandatory` and closes its channel, so a publish returns only once the broker holds the message and a consumer acks its input only after its downstream messages are safe (ADR-D60, phase 3).
