## Las dos migraciones, con su SQL

La base viva esta en `f2a8c41d9e37`; la cabeza de `develop` es `b4e82f17c9a3`
via `a7c3e91b4d26`. Ensayado en seco con `alembic upgrade --sql`, que no toca
nada:

```sql
BEGIN;
-- f2a8c41d9e37 -> a7c3e91b4d26
CREATE TABLE swissprot_release (...);           -- tabla nueva
CREATE INDEX ix_swissprot_release_published_at ...;
CREATE INDEX ix_swissprot_release_job_id ...;
CREATE TABLE swissprot_membership (...);        -- tabla nueva
-- a7c3e91b4d26 -> b4e82f17c9a3
ALTER TABLE embedding_config ALTER COLUMN max_length DROP NOT NULL;
COMMIT;
```

**Es lo mas benigno que puede ser un cambio de esquema**, y conviene decir por
que en lugar de pedir confianza:

- las dos tablas son **nuevas**: ninguna fila existente se lee ni se reescribe;
- el `ALTER` **relaja** una restriccion, asi que no puede fallar por datos que ya
  esten ahi, y `embedding_config` tiene 8 filas, de modo que el bloqueo es
  instantaneo;
- todo va en **una transaccion**: o entran las dos migraciones o ninguna;
- no hay backfill, no hay `UPDATE` sobre datos, y no se toca ninguna de las
  tablas grandes (`protein_go_annotation` tiene 649.889.442 filas y esto no la
  mira).

La bajada de `b4e82f17c9a3` **se niega** si alguna fila tiene `max_length` nulo,
en vez de inventarle un punto de truncamiento que nunca se aplico.
