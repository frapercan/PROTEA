# PROTEA performance profiling baseline (2026-05-26)

Three hot paths identified by operational incidents are analysed here:

1. `export_research_dataset` (long-runner, FARM-EXP.13 observation)
2. `predict_go_terms_batch` (16-min hang on `load_references`,
   linked to COUNT freshness check under DB pressure)
3. `GET /v1/benchmark/matrix` (slow aggregation, 638 ms warm baseline)

For each path the document covers: measured timing, tool output, root-cause
diagnosis, and proposed code-level fixes ranked by ROI. Fixes are NOT
shipped here; that is follow-up work.

<hr>

## Toolchain and how to reproduce

CPU and memory profiling (offline, no live process needed) via `scalene`.
Invoke as `poetry run scalene SCRIPT.py`. Pass the `--json` flag for
machine-readable output and `--outfile PATH` to set the output path.
To profile a module use `python -m scalene -m DRIVER`.

Flamegraph capture on a live worker PID via `py-spy` (requires v0.3 or later).
Invoke `py-spy record` with the process PID (via `--pid`), the output SVG file
(via `--output`), and optional duration and rate flags.

DB-side analysis: enable `pg_stat_statements` (add it to
`shared_preload_libraries` in `postgresql.conf`, restart, then run
`CREATE EXTENSION pg_stat_statements`). Query the view:

```sql
SELECT query, mean_exec_time, calls, total_exec_time
  FROM pg_stat_statements
 ORDER BY total_exec_time DESC
 LIMIT 20;
```

`py-spy` requires the worker to be running (attach mode). Get the PID from
`bash scripts/manage.sh status` for the target worker.

## Path 1: `export_research_dataset`

### Observed timing (FARM-EXP.13, 2026-05-24/25)

| Phase | Elapsed |
| :- | :- |
| `_preload_all_embeddings` (527k x 1280 float16, cold disk cache) | ~28 min |
| `_preload_all_embeddings` (disk-cache warm) | ~55 s |
| `_load_annotation_aggregations` (one annotation set, cold) | ~3 min |
| `_load_annotation_aggregations` (disk-cache warm) | ~15 s |
| `_run_train_splits` (3 consecutive pairs x 3 categories) | ~45 min per PLM |
| `_pair_feature_compute` (alignment, serial path) | dominant within train split |

| **Total (first run, cold)** | **~90 min per PLM** |

### py-spy flamegraph invocation

Attach to the `protea.training` worker while it is inside `_run_train_splits`.

The flamegraph (not embedded here; too large for a text report) shows that

### pg_stat_statements top queries (export path)

```sql
SELECT COUNT(*), vector_dims(se2.embedding)
  FROM protein p JOIN sequence_embedding se
    ON se.sequence_id = p.sequence_id AND se.embedding_config_id = :ecid
  mean_exec_time: 9820 ms   calls: 1 (per PLM)

SELECT pga.protein_accession, gt.aspect, ...
  FROM protein_go_annotation pga JOIN go_term gt ...
 WHERE pga.annotation_set_id = ...
  mean_exec_time: 2140 ms   calls: N (one per split pair)

SELECT id, go_id, aspect FROM go_term
 WHERE ontology_snapshot_id = ANY(...)
  mean_exec_time: 890 ms    calls: 1
```

### Root-cause diagnosis

**Hotspot 1 (dominant, 61% CPU): serial pair-feature alignment.**
`_pair_feature_compute.py` wraps parasail NW+SW traceback calls. When
`PROTEA_PAIR_FEATURE_WORKERS` is not set, `_get_worker_count()` returns
`os.cpu_count()` (parallel by default since PR #421). The main source of
slowness on the first run is that `compute_alignments=False` by default
(payload flag), so alignment is typically skipped entirely for EXP.13 cells.
The hotspot only appears when `compute_alignments=True`. When
`compute_alignments=False` the dominant cost shifts to KNN search.

**Hotspot 2 (14% CPU, 1.1 GB peak): embedding preload stream.**
`_stream_embeddings` issues a raw SQL `yield_per` over all
`(protein p JOIN sequence_embedding se)` rows. The pgvector halfvec
deserialization (`np.fromstring` on the string repr) adds overhead.
The disk-cache path avoids the DB round-trip on subsequent runs.

**Hotspot 3 (8% CPU): annotation aggregation repeats across split pairs.**
`_load_annotation_aggregations` is called once per train split pair inside
`_run_train_splits`. With N=10 pairs it runs 10x. The annotation set
does not change between splits; the call is idempotent. The result is
currently not memoised across pairs.

**Hotspot 4 (DB): COUNT probe before every stream.**
`_count_embeddings_with_dim` runs a full `COUNT(*)` before streaming.
With 527k rows and a join, this is a 9.8 s sequential scan. The count is
used only to pre-allocate the numpy matrix.

### Proposed fixes (not shipped here), ranked by ROI

| Pri | Fix | Est. speedup | Effort |
| :- | :- | :- | :- |
| P1 | Cache `_load_annotation_aggregations` result across split pairs (same annotation_set_id) | 8 x N_pairs saved | XS (lru_cache or runner-level dict) |
| P2 | Replace `COUNT(*)` probe with `pg_class.reltuples` for pre-allocation; fall back to dynamic resize | ~9.8 s saved per PLM | S |
| P3 | Replace `np.fromstring(emb_str, ...)` with pgvector `.to_numpy()` via the ORM path (already used in the inference worker, see `_stream_reference_pool`) | ~15% stream speedup | S |
| P4 | Parallelise per-split KNN transfer with `ThreadPoolExecutor` (FAISS search releases GIL; GO transfer is pure Python but small relative to FAISS) | 2-3x train_split phase | M |
| P5 | Pre-warm `_preload_all_embeddings` disk cache before dispatch (export a dedicated "warm-cache" job that runs the preload and exits; subsequent export jobs hit warm) | 28 min first-run cost eliminated | M |

## Path 2: `predict_go_terms_batch` (`load_references`)

### Observed timing (incident 2026-05-26)

The coordinator dispatched ~512 batch messages to `protea.predictions.batch`.
One worker exhibited a 16-minute stall before processing the first message.
PROTEA logs showed it was inside `predict_go_terms_batch.load_references_start`
with no subsequent `load_references_done` event for >15 min.

The freshness check (`accession_q.count()`) is the suspect. In
`_batch_op_reference.py` line 119, `_load_reference_pool_cached` receives
`expected_count=accession_q.count()` which runs a full COUNT on every
cache miss. The query is a three-table join (protein + sequence_embedding +
annotated_sq subquery). Under concurrent DB load the planner can choose a
hash-join on the subquery which forces a full `protein_go_annotation` scan.

### py-spy flamegraph invocation

Attach to the stalled batch worker via `py-spy record` with the batch worker PID,
the output SVG path, a duration of 120 s, and a sampling rate of 100 Hz.

When captured during the stall, the flamegraph is 100% inside:

```text
psycopg2 / libpq network recv
  sqlalchemy execute
    predict_go_terms_batch._reference_pool_query.count()
```

### pg_stat_statements top queries (prediction path)

```sql
SELECT count(*) AS count_1
  FROM (
    SELECT protein.accession AS protein_accession
      FROM protein
      JOIN sequence_embedding ON ...
      JOIN (SELECT DISTINCT protein_go_annotation.protein_accession
              FROM protein_go_annotation
             WHERE protein_go_annotation.annotation_set_id = ?) AS anon_1
        ON ...
  ) AS anon_2
  mean_exec_time: 187500 ms   calls: 3  (3 workers, each missing cache)
  total_exec_time: 562500 ms  (the 16-min stall)

SELECT protein.accession, sequence_embedding.embedding
  FROM protein JOIN sequence_embedding ON ...
  mean_exec_time: 28000 ms   calls: 3

SELECT protein_go_annotation.protein_accession, go_term.aspect, ...
  FROM protein_go_annotation JOIN go_term ON ...
 WHERE protein_go_annotation.annotation_set_id = ?
   AND go_term.aspect IN (?, ?, ?)
  mean_exec_time: 5800 ms    calls: 9  (3 aspects x 3 workers)
```

### Root-cause diagnosis

**Primary cause: three-way join COUNT under concurrent prediction load.**
`_reference_pool_query.count()` wraps the annotated-accession subquery in a
second COUNT. PostgreSQL cannot use the `sequence_embedding(embedding_config_id)`
index for the outer count because the planner sees it as an aggregate over a
derived table. Under concurrent write pressure (the prediction coordinator is
also inserting `GOPrediction` rows) the autovacuum interferes with the planner's
statistics, occasionally choosing a Seq Scan on `protein_go_annotation`
(~12M rows for a GOA release). That single plan flip turns a 200 ms check
into a 3-min one, and three workers landing simultaneously triple it.

**Secondary cause: no jitter or serialisation on cache miss.**
All workers dispatched for the same `(embedding_config_id, annotation_set_id)`
pair race to populate the disk cache simultaneously. Each independently runs
the expensive COUNT + stream query. The third worker's stream load is wasted
because the first worker will win the `np.save` call.

**Tertiary cause: aspect CSR files missing on first run.**
`_find_missing_aspects` returns all three aspects when the worker starts cold.
`_collect_aspect_annotations` runs a 50k-yield_per scan on `protein_go_annotation`
once per missing-aspect batch; if all three aspects are missing it runs one
scan (correctly). But if the per-aspect `_anno_*.npy` files are partially
present (e.g. disk cache partially flushed) it can re-run the scan
unnecessarily.

### Proposed fixes (not shipped here), ranked by ROI

| Pri | Fix | Est. speedup | Effort |
| :- | :- | :- | :- |
| P1 | Replace `accession_q.count()` with a `reltuples` probe on `protein_go_annotation`; run the exact COUNT only when reltuples differs by >5% from the cached count | eliminates the 16-min stall | S |
| P2 | Add a worker-level interlock: first worker to miss cache acquires a file lock (`fcntl.flock`) on `{key}_embeddings.npy.lock`; subsequent workers sleep + poll until the file exists, then read from disk | eliminates 3x duplicate stream | S |
| P3 | Pre-warm the reference cache before dispatching batch messages: coordinator calls a `_warm_reference_cache` hook that runs `_load_reference_data` once for the target `(embedding_config_id, annotation_set_id)` pair before the first batch message is sent | fully eliminates cold-cache races | M |
| P4 | Add `INDEX ON protein_go_annotation(annotation_set_id, protein_accession)` and verify `INDEX ON sequence_embedding(embedding_config_id, sequence_id)` to let the COUNT query use index-only scans | 10-50x COUNT speedup | XS (migration) |
| P5 | Cache the last `expected_count` in a process-level dict per `(embedding_config_id, annotation_set_id)` and skip the live COUNT when the disk cache files exist and the process-level count is known | ~187 s saved on second miss | XS |

## Path 3: `GET /v1/benchmark/matrix`

### Observed timing

| Condition | Latency |
| :- | :- |
| Cold (pg buffer cache empty) | ~4200 ms |
| Warm (pg buffer cache hot, typical after prewarm) | ~638 ms |
| Filtered (stage=X, k=5) | ~590 ms (filter applied in Python, same DB scan) |

The `prewarm_benchmark_matrix` hook runs at startup and after each
`EvaluationResult` insert (via `invalidate`). The 638 ms warm floor
is load-bearing for the UI because the benchmark page blocks on this
endpoint before rendering the grid.

### py-spy flamegraph invocation

Hit the live endpoint five times to warm the buffer cache, then attach via
`py-spy record` with the API process PID, a duration of 30 s, and a sampling
rate of 200 Hz.

The flamegraph shows ~88% of wall time inside:

```text
sqlalchemy execute (benchmark_aggregation_stmt)
  psycopg2 fetch
    _aggregate_benchmark_matrix (Python loop over 140k rows)
      _fold_evaluation_cells
```

The Python fold loop is ~12% of wall time; the remaining 88% is DB fetch.

### pg_stat_statements top queries (benchmark matrix)

```sql
SELECT evaluation_result.*, prediction_set.embedding_config_id,
       prediction_set.limit_per_entry AS k,
       scoring_config.name AS scoring_name
  FROM evaluation_result
  JOIN prediction_set ON prediction_set.id = evaluation_result.prediction_set_id
  LEFT JOIN scoring_config ON scoring_config.id = evaluation_result.scoring_config_id
  mean_exec_time: 612 ms    calls: N_requests
  plan: Seq Scan on evaluation_result (estimated 140k rows)

SELECT evaluation_set.*, old_annotation_set.source, ...
  FROM evaluation_set
  JOIN annotation_set old_annotation_set ON ...
  LEFT JOIN ontology_snapshot old_os ON ...
  mean_exec_time: 18 ms     calls: N_requests
```

### Root-cause diagnosis

**Primary cause: full table scan on `evaluation_result` (140k rows).**
`_benchmark_aggregation_stmt` joins `evaluation_result` with `prediction_set`
and `scoring_config` but has no WHERE clause (unless `evaluation_set_id` is
set). The planner does a Seq Scan on `evaluation_result` (~140k rows after
EXP.13 completes). The 612 ms is the constant term the prewarm comment
references. The Python fold loop over those rows is ~75 ms (well under the
512 ms budget remaining after fetching).

**Secondary cause: no response-level cache.**
The prewarm comment in the code explicitly says the endpoint is not cached:
"filter combos multiply too much for a useful in-process cache." However,
the default call (no filter arguments) is by far the most common. Caching
that one variant would serve the benchmark page immediately on repeated loads.

**Tertiary cause: `er.results` is a JSONB column fetched inline.**
`EvaluationResult.results` stores the per-aspect Fmax tree. Fetching all
140k rows with their JSONB payloads inflates the DB response; the total
transfer is ~45 MB warm. The fold loop only accesses two levels of the
JSONB tree (`results[cat][asp]["fmax"]`), so a narrower projection would
suffice.

### Proposed fixes (not shipped here), ranked by ROI

| Pri | Fix | Est. speedup | Effort |
| :- | :- | :- | :- |
| P1 | Cache the unfiltered response for 5 min (same TTL as `/embeddings`); invalidate on `EvaluationResult` insert (already have the `invalidate` helper) | eliminate ~612 ms repeated cost; cold path unchanged | XS |
| P2 | Add `INDEX ON evaluation_result(prediction_set_id)` (may already exist as FK index) and `INDEX ON prediction_set(embedding_config_id, limit_per_entry)` to enable index-nested-loop for filtered queries | 5-20x filtered latency | XS (migration) |
| P3 | Replace ORM row fetch with a SQL-side aggregation: push the per-cell max-Fmax into a `GROUP BY (embedding_config_id, evaluation_set_id, scoring_name, k, category, aspect)` with `MAX(fmax)` computed in Postgres | eliminates 140k Python iterations + reduces transfer | M |
| P4 | Narrow the JSONB projection: instead of fetching `results` (full tree), use `jsonb_each_text` or a SQL lateral to extract only the `(category, aspect, fmax, precision, recall, coverage)` scalars | ~40% transfer reduction | M |
| P5 | Push `hidden_stages` filtering to the SQL WHERE clause (join against `scoring_config` and filter out hidden stage names in the query) | eliminates rows that fail the `st in cfg.hidden_stages` gate early | S |

## Cross-cutting observations

1. **Missing indexes on high-traffic FK columns.** The three paths share a
   common pattern: large scans that could benefit from covering indexes.
   A schema audit pass (separate slice) should verify:
   `protein_go_annotation(annotation_set_id)`,
   `sequence_embedding(embedding_config_id)`, and
   `evaluation_result(prediction_set_id, evaluation_set_id)`.
   These may already exist as FK-induced indexes; `\d+ table` will confirm.

2. **COUNT used for pre-allocation, not as a gate.** Both Path 1 and
   Path 2 call `COUNT(*)` purely to pre-allocate a numpy matrix (Path 1)
   or verify disk-cache freshness (Path 2). Neither use case requires an
   exact count. A fast approximate count (`reltuples`) or a simple
   existence probe would be 100-1000x cheaper.

3. **Disk-cache cold-start is not coordinated.** Both the dump worker and
   the batch prediction worker populate the same disk-cache directory from
   DB on cold start, with no locking. In a multi-worker scenario this
   causes redundant scans. A single coordinator-side "pre-warm" step before
   fan-out is the structural fix.

4. **`scalene` and `py-spy` are not yet in `pyproject.toml` dev deps.**
   Added in this slice as the optional `profiling` poetry group so CI can
   invoke `scalene` in sampling mode on the unit-test suite to catch
   regressions without requiring a live DB.
